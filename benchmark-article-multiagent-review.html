Agent 编排：Team 模式 + 并行 Spawn 推荐使用 Team 模式进行编排。主 Agent（或 PM Agent）作为 team-lead，通过 TeamCreate 创建团队后，在单条消息中同时 spawn 三个评审 Agent，实现真正的并行执行。 编排方式TeamCreate → 主 Agent 作为 team-lead 并行 spawn一条消息中 3 个 Agent 调用（QA + FE + BE） 结果回收主 Agent 等待三个 Agent 返回后，spawn 汇总 Agent 通信方式SendMessage + 共享任务列表（TaskList） 为什么并行而非串行？ 三个角色审查 PRD 是无依赖关系的独立任务。串行执行总耗时 = QA + FE + BE，并行执行总耗时 = max(QA, FE, BE)，通常可节省 60% 以上时间。且并行避免了先执行的 Agent 结论影响后执行的 Agent（锚定偏差）。 7.2 上下文管理：Prompt 注入而非文件共享 PRD 文档通过 prompt 直接注入传递给每个评审 Agent，而非写入文件再让 Agent 读取。优势： 无需文件 IO，减少失败点 每个 Agent 的上下文完全隔离，只看到 PRD + 自己的角色 Prompt 汇总 Agent 通过 prompt 注入三方 JSON 结果，解析确定性高 注意 Token 上限 PRD 过长时（超过 8000 字），考虑按章节拆分评审，或使用 RAG 检索相关章节注入。对于多数互联网产品 PRD（3000-6000 字），直接注入无压力。 7.3 结构化输出：强制 JSON 格式 评审 Agent 必须输出严格 JSON，而非自然语言。这是汇总 Agent 能正确解析、去重、排序的前提。 在 Prompt 末尾明确要求"只输出 JSON，不要输出其他内容" 提供 JSON Schema 示例，确保字段一致 汇总 Agent 收到 JSON 后可直接 JSON.parse，无需模糊解析 7.4 问题去重策略 不同角色可能提出相同或相似的问题（如 QA 和 FE 都问到"金额为负数的处理"）。汇总 Agent 的去重逻辑： 完全重复问题文本相似度 > 90% → 合并为一条，标注多个提出者 语义重复不同表述但指向同一问题 → 合并，保留最详细的表述 关联问题不同角度但同一根因 → 保留各自条目，在答案中统一回应 7.5 迭代评审机制 第一轮评审后，如果存在 high 级别未解决问题，PM Agent 根据 HTML 报告修订 PRD，重新触发评审。建议： 最大轮次 ≤ 3 轮，避免无限循环 第二轮起，评审 Agent 只审查修订部分，不再全量审查 每轮报告标注轮次编号，便于追踪问题收敛过程 7.6 容错与降级 Agent 超时设置超时阈值（建议 120s），超时后该角色问题列表为空，继续汇总 JSON 解析失败汇总 Agent 尝试从自然语言中提取问题；失败则标注"该角色评审异常" 部分 Agent 失败降级为两方评审，报告中标注缺失角色 汇总 Agent 失败将原始 JSON 问题列表直接输出，由人工处理 7.7 角色可扩展性
