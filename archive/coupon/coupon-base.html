一句话结论：需求梳理的「已有 / 暂无 / 待扩展」判定在 产品端（UI / 功能有无） 层面基本成立；但本技术分享首次揭示真实后端底座 = gruul-mall 的 addon-coupon 独立模块（订单服务通过扩展点调用，不直接写券表）。因此所有「待扩展 / 新增」必须再切一层：改后端 addon-coupon vs 仅补前端。下文给出逐项校准、关键技术约束与对范围判定的修正建议。

架构与核心表

优惠券数据由 addon-coupon 独立维护，订单服务（gruul-mall-order）通过 addon 扩展点调用，不直接写优惠券表。主要表：

  • t_coupon：券定义（店铺/类型/状态/生效方式/门槛/优惠/库存/限领/商品范围）
  • t_coupon_user：用户领取后快照（用户/店铺/原券id/状态/有效期/规则快照/商品范围快照）
  • t_coupon_product：券与指定/排除商品关系
  • t_coupon_order_record：订单用券记录（PK order_no，coupons=店铺id→用户券id 的 map，平台券店铺id=0）
  • t_coupon_calculate：结算页临时计算表（bid 关联本次金额）

枚举

CouponType： PRICE_REDUCE 无门槛现金 · PRICE_DISCOUNT 无门槛折扣 · REQUIRED_PRICE_REDUCE 满减 · REQUIRED_PRICE_DISCOUNT 满折
CouponStatus： OK（前端按日期/库存派生 未开始/进行中/已结束）· BANED 平台下架 · SHOP_BANED 店铺下架
EffectType： PERIOD 固定日期段 · IMMEDIATELY 领取后 N 天
CouponProductType： ALL 平台全部 · SHOP_ALL 店铺全部 · ASSIGNED 指定可用 · ASSIGNED_NOT 指定不可用

生命周期与关键机制

制券 → 领券（Redis 扣库存 + 异步 DB + 生成 t_coupon_user 快照）→ 结算页查可用券 → 下单核销（校验 used/有效期/商品范围/门槛，锁券置 used=true）→ 关单返还（MQ coupon.order.closed 恢复 used=false）。
关键机制：领取后下单使用的是 t_coupon_user 上的规则快照，而非实时读 t_coupon。订单侧只消费 OrderDiscount.sourceAmount，优惠分摊逻辑（3 轮分摊）可复用。

已知限制 / BUG（直接影响需求范围）

限制 不支持每满减：满 200 减 50，下单 400 仍只减 50。根因 validCouponUser 只校验一次门槛、getDiscountAmount 返回 min(total, amount)。需新增 rule_mode（SINGLE / EVERY_FULL）字段。

限制 平台/后台赠送无法指定店铺 / 商品：giftsToUser 调用 newCouponUser(..., null)，productIds 为 null，不保存商品范围快照。

BUG 店铺级关单返还误恢复：orderClose 在 SHOP 关闭时把整单 coupons map 传给 unlockUserCouponBatch，会遍历把未关闭店铺券、甚至平台券也恢复为未使用。多店铺 / 平台券场景有资损风险。

一致 售后（AFS）不退券：与需求梳理「不做售后退券」完全一致。

三、关键发现与待决策

1平台端「无制券」的本质 = 后端设计约束

AdminCouponController.newCoupon 强制取 getShopId()，券定义必带店铺作用域；平台券只能走 giftsToUser（不落 t_coupon 主券，直接批量生成 t_coupon_user 快照，平台券在 t_coupon_order_record.coupons 中 key=0）。→ 平台端「发券」= 指定发券，不是制券。需求梳理判定正确，且现在有了技术依据。

2每满减缺口（新增技术约束）

现有引擎只支持「满减一次」。若本期任何满减券需支持「每满递减（满200减50，400减100）」，属 🟠待扩展，需改 addon-coupon：t_coupon/t_coupon_user 增 rule_mode(SINGLE/EVERY_FULL) + 校验/结算SQL/前端「计算模式」选项。需求梳理未显式提及每满减，需确认本期是否纳入。

3首单限制缺口

商家端制券「待拓展：首单」→ 后端 CouponType / 校验逻辑无首单约束字段，需新增。属 🟠待扩展（后端改 addon-coupon）。

4指定发券商品范围

gifts 当前 productIds=null，平台/后台赠送无法指定店铺/商品。补「商品范围快照逻辑」即可，中等工作量，复用 t_coupon_product。这与需求梳理「指定发券待扩展」完全对应，技术路径已明确。

5关单返还 SHOP 级 BUG 风险 ❗

资损风险：店铺级关单时当前实现把整单 coupons map 传入解锁，会把未关闭店铺券、甚至平台券也恢复为未使用。若本期涉及多店铺订单 / 平台券 + 后台关闭返还，需研发先修此 BUG，否则「后台关闭订单可返还（已有功能无改动）」的判定在多店铺场景不成立。建议列为依赖项 / 待确认。

6App 端「暂无」实为前端缺口

后端 ConsumerCouponServiceImpl（collectCoupon / orderShopCouponPage / useCoupon）已完整支持领券、结算、核销。App 的「我的优惠券 / 商品详情领券 / 下单核销 暂无」是客户端 UI / 调用缺口，非后端缺口。→ App 相关项工作量低于「后端新增」，排期应区别于平台端发券活动类需求。

7直播时长发券 = 净新增引擎（复用 gifts）

需求梳理「本期仅直播时长发券写死规则」是净新增触发源：火山引擎直播进入/退出时间 → 时长 > x 的用户列表 → 批量调 giftsToUser 发券。后端无此活动实体，需新引擎；发券动作复用现有 gifts 接口。关键依赖 = 火山引擎接口（需确认返回字段）。

四、对范围判定的修正建议

  • 维持：平台端无制券、售后不退券、小程序/H5 已有功能、删除券本期不做。
  • 细化：所有「待扩展 / 新增」在原判定后追加缺口类型（改后端 addon-coupon / 仅前端），便于研发排期与工作量评估（见 §二 末列）。
  • 新增待确认（技术驱动）：
    1. 本期是否纳入每满减（rule_mode）？
    2. 商家端制券是否补首单限制？
    3. 关单返还 SHOP 级 BUG 是否在本期顺带修复（多店铺/平台券场景）？
    4. 商家端「编辑券」是否补 UI 入口（后端已有能力）？
  • 历史判定修正：之前四象限「现有体系全是原型无后端」指的是泰小虎自有 Flask 后端（admin_service.py 零券代码）；真实券引擎在 gruul-mall addon-coupon。需求梳理的「已有」应理解为「gruul-mall 已支撑 + 某端已落地 UI」，二者不矛盾，但须在 PRD 中写清底座归属。
