① WorkBuddy专家团：实现多 agent 协作【需求评审】，只要这几步！

  • 链接：https://mp.weixin.qq.com/s/tVOEfm7oAoKvES9WNJnwpQ
  • 作者 / 来源：道三（微信公众号）
  • 发布时间：2026-08 前后
  • 全文在线版：多 Agent 需求评审 · 全文（仿写时直接读）
  • 一句话主题：用 WorkBuddy「专家团（Team）」能力，让测试 / 前端 / 后端三个 Agent 并行审同一份 PRD，再由汇总 Agent 产出带角色颜色区分 + 严重度排序的 HTML 评审报告，模拟真实研发评审会。

可仿写的文章骨架（结构即方法论）：

  1. 概述（目标 + 工作流总览 + 核心设计原则）
  2. Agent 角色定义（输入 / 输出 / 核心职责表格）
  3. 各角色审查关注点详解（逐角色审查清单）
  4. 工作流阶段（PRD 生成 → 并行评审 → 汇总输出 → 迭代修订）
  5. 通信协议（Agent 间数据流 + 问题结构化 JSON Schema）
  6. Prompt 模板（每个角色一份可直接抄的 prompt）
  7. HTML 输出规范（颜色编码体系 + 报告结构）
  8. 可行性建议（编排 / 上下文 / 结构化输出 / 去重 / 迭代 / 容错 / 可扩展）
  9. 实现路径（P0~P4 分阶段）

可直接借鉴的 8 个抓手：

  1. 结构化 JSON 输出：评审问题统一 {agent_role, questions:[{id,category,severity,question,prd_section,suggestion}]}，便于程序化去重/排序。
  2. 并行 Team 编排：QA+FE+BE 同一条消息 spawn，耗时 = max 而非累加，省 60%+。
  3. 角色隔离 + Prompt 注入：每个 Agent 只看到 PRD+自身角色 prompt，避免锚定偏差。
  4. 严重度三档：high（阻塞）/ medium（补充）/ low（优化），优先清 high。
  5. 颜色编码报告：测试=琥珀、前端=蓝、后端=绿、PM 答案=紫，一眼定位。
  6. 待确认项汇总：所有「需 PM 确认」单独成表，闭环不漏。
  7. 迭代机制：≤3 轮，第二轮起只审修订部分，标注轮次追踪收敛。
  8. 容错降级：单 Agent 超时/失败 → 降级两方评审，不阻断整体。

结论：强相关、能直接优化，而且和我们已有能力高度同构，主要缺口在「结构化输出格式」和「并行编排」，补上即可显著提效。

2. 落地到 PRD 输出的 3 个最值钱优化（建议优先级）

  • P0｜评审问题结构化：在 pm-review-board 输出里强制 JSON 协议（id/category/severity/prd_section/suggestion），并新增「§待确认项」表，直接喂给我们的 PRD 红字/待确认机制（你 PRD 规范里已有「⚠️ 待确认 @干系人」占位）。
  • P1｜报告颜色编码 + 严重度排序：套用文章的颜色规范生成 HTML 评审报告，high 优先、待确认项置顶，评审结论给「通过/有条件通过/不通过 + 阻塞项数量」。
  • P2｜并行 Team 编排 + 迭代复审：在 pm-master 下把多角色评审改为并行 spawn，并支持修订后增量复审（≤3 轮），把「评审—修订—再评审」做成闭环。

3. 风险与注意

  • 文章是「评审工作流」设计稿，不是 PRD 内容写作模板；它优化的是「PRD 被审得更干净」，而非「PRD 怎么写」。我们 PRD 的章节结构仍应以你桌面《PRD 输出规范（修订于260715）》的「一~九」为准。
  • JSON 强制输出对长 PRD（>8000 字）有 token 压力，文章建议按章节拆分或 RAG；我们泰小虎 PRD 体量偏大，落地时需注意分章注入。
  • 文章角色偏研发侧，我们的 pm-review-board 还含运营/法务，扩展时按文章「角色配置化」思路加 prompt+颜色即可。
