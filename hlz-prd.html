二、项目背景与目标

2.1 业务背景

当前泰小虎积分体系（后端称「虎力值」）已有完整数据模型（user_points 账户表 + point_transactions 流水表）和 earn/consume 方法，但缺少运营侧手动干预能力：

  • 运营无法对用户批量赠送或扣除虎力值（如客服补偿、活动奖励补发、违规处罚等场景）。
  • 现有 App 端「变动记录」页仅展示任务类记录（文本为「完成xxx任务」），不展示后台人工操作的理由，用户看到的是模糊的任务名而非实际原因。
  • 存量积分管理页面（admin_points.html）为只读展示页，不支持批量操作。

本期需求在平台端后台「App管理」页签下新增「虎力值管理」模块，提供批量赠扣能力 + 操作记录追溯；同时增强 App 端变动记录展示，将原任务名替换为后台选择的理由。

2.2 项目目标

目标维度具体目标
业务目标赋予运营批量干预虎力值的能力（赠送/扣除），覆盖补偿、补发、处罚场景。
用户目标App 用户可在变动记录查看每次增减理由（替代模糊「完成xxx任务」）。
技术目标复用 earn/consume；新增 source='admin' 分支。

2.3 衡量指标

指标定义衡量方式
批量操作成功率后台提交批量赠扣请求的成功比例后端日志统计
操作记录可追溯率每笔赠扣操作均可通过记录表查到明细（用户清单+各自数值）功能验收
App 变动记录理由覆盖率变动记录中含「理由」列的比例（目标 100%）UI 验收

逐步操作逻辑：

  1. 运营进入「App管理」→「虎力值管理」页签，页面加载时默认查询近 30 天全部类型的操作记录，按操作时间倒序排列。

业务逻辑与边界条件
统一筛选逻辑（点击「搜索」一次性触发）

逐步操作逻辑：

  1. 选择筛选条件（二选一）：运营在统一筛选区选择一种方式——① 活动标签：下拉单选一个活动标签（双11大促/周年庆/新人专享/会员日/沉睡唤醒/618复盘，已确认固定枚举）；或 ② 手机号：输入框填写手机号（支持精确/模糊）。两者不可同时填写。
  2. 点击「搜索」触发（核心）：若活动标签与手机号同时填写，前端直接提示「活动标签与手机号不可同时搜索，请只保留一种方式」并拦截；否则按所选方式调用 GET /api/admin/users?tag=活动标签 或 GET /api/admin/users?phone=手机号 向服务端发起查询，返回用户集合。
  3. 结果回显：返回的用户直接追加进「目标用户列表」并去重（已存在的 uid 不重复添加），列表计数实时刷新为「目标用户：N 人」；若无可匹配用户，Toast 提示「未找到符合条件的用户」。
  4. 点击「重置」：清空筛选输入（活动标签下拉、手机号），并仅移除由筛选命中的用户（导入的用户保留），目标用户列表计数同步刷新。

统一筛选与批量导入两种方式相互独立又合并生效：最终「目标用户列表」= 筛选命中 ∪ 导入，点击底部「确认赠送 / 确认扣除」即对该清单全部用户执行操作，无需二次勾选确认。

「确认赠送」逐步操作逻辑：

  1. 前置校验：目标用户列表不能为空 → 提示「请先通过筛选或导入选择人员」；数量必须为正整数且 > 0 → 提示「请输入有效的赠送数量」；理由必选 → 提示「请选择操作理由」；备注必填且 ≤ 500 字 → 为空提示「请填写备注」，超长提示「备注超出 500 字上限」。
  2. 提交请求：前端收集 user_ids[]（目标用户列表全部 uid）+ points（正整数）+ reason（所选理由文本）+ remark（备注文本）+ operator（当前登录账号），POST 到 /api/admin/points/grant。
  3. 后端处理：遍历 user_ids，对每个用户调用 earn_points(user_id, points, source='admin')，更新 user_points.available += points；同时 INSERT 一条 point_transactions 记录（source='admin', points=+N, reason, operator, balance_after）。
  4. 生成操作记录：所有用户处理完毕后，INSERT 一条 admin_point_operations 记录（operation_type='grant', total_points=+N*count, reason, remark, operator, affected_count=count）。
  5. 返回结果：后端返回 {success:true, affected_count:N, operation_id:xxx}；前端 Toast「赠送成功，共影响 N 位用户」并关闭弹窗，刷新列表。

「确认扣除」逐步操作逻辑：

  1. 前置校验：同赠送（目标用户列表非空、数量有效、理由必选、备注必填 ≤ 500 字）。
  2. 提交请求：POST 到 /api/admin/points/deduct，参数同上（points 为正整数，后端取负；含 remark）。
  3. 后端处理：遍历 user_ids，调用 consume_points(user_id, points, source='admin')。不校验余额，user_points.available -= points 可为负数。
  4. 写流水 + 操作记录：同赠送流程，points 存负值（如 -100），operation_type='deduct'，记录含 remark。
  5. 返回结果：Toast「已扣除 X 虎力值，共影响 N 位用户」并刷新列表。

异常分支：

  • 用户不存在（ID/手机号无效）→ 该用户跳过并在结果中标记失败，不影响其他用户处理；最终 Toast 中注明「其中 M 位用户处理失败」。
  • 网络超时 → 显示「操作超时，请稍后重试」，不自动重试（防止重复扣款）。
  • 导入模板解析失败（格式错误/列为空）→ 提示「导入文件格式不正确，请下载标准模板填写」。

计算公式：变动总虎力值 = 单用户数量 × 已选用户数。赠送时为正值，扣除时为负值。

数据来源：人员检索调 GET /api/admin/users/search；提交分别调 grant/deduct API；理由枚举取自有字典（非本期新建）。

5.1 埋点需求

本需求埋点事件与属性严格遵循《泰小虎埋点规范 v2.3》（在线全文，含完整 30 事件/属性/页面枚举/友盟约束）。

本期涉及事件清单：

事件英文名事件显示名所属层平台触发时机必含上报参数(友盟中文名)备注
本期暂不埋点（后续有统计诉求再补，不新增 admin_operate 事件）
———平台端后台运营点击「确认赠送」操作类型、理由、影响用户数、变动总量已确认：本期不埋点，后续补
———平台端后台运营点击「确认扣除」同上可与赠送合为同一事件，以操作类型区分

注：以上事件清单为初步评估，具体事件定义须严格从《泰小虎埋点规范 v2.3》既有 30 事件目录中选取或走新增评审。禁止凭空编造事件英文名或属性变量名。

5.2 性能要求

  • 批量操作（单次 ≤ 100 人）后端响应时间 ≤ 3 秒。
  • 操作记录列表查询（默认分页 10 条）响应 ≤ 500ms。
  • App 变动记录页首次加载 ≤ 1 秒。

5.3 安全要求

  • 虎力值管理功能仅限「平台管理员」角色（含「虎力值管理」权限点）访问，复用现有角色体系、不新建角色（已确认）。
  • 所有写操作（赠送/扣除）记录操作人（operator），不可篡改，用于审计追溯。
  • 扣除操作允许负数余额，但后端仍记录完整流水，确保可追溯。
